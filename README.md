# poke-env PPO Doubles Agent

学習側・対戦相手側の双方で対戦ごとにパーティをランダム生成し、選出・技・対象・交代を学習します。

## 前提
- 確認環境: Python 3.12.4 / poke-env 0.9.0 / PyTorch 2.7.1 / NumPy 2.2.5
- ローカル Pokemon Showdown サーバー起動済み（localhost:8000）
- コマンドは `doublebattle` ディレクトリで実行

## インストール

```bash
pip install -r requirements.txt
```

## ローカルShowdown起動例

```bash
git clone https://github.com/smogon/pokemon-showdown.git
cd pokemon-showdown
node pokemon-showdown start --no-security
```

## 学習

```bash
python train.py
```

対戦形式は全段階 `gen9vgc2024regg` です。

| 段階 | 学習側 | 対戦相手 | 対戦数 |
|---|---|---|---:|
| 1 | PPO + ランダムパーティ | ランダム行動 + ランダムパーティ | 1,000 |
| 2 | 継続したPPO + ランダムパーティ | ダメージ重視 + ランダムパーティ | 1,000 |
| 3 | 継続したPPO + ランダムパーティ | 同じPPOを共有 + ランダムパーティ | 1,000 |

- 対戦ごとに双方の6体・技4個・特性・持ち物の割当を独立に抽選し、6体から4体を選出します。
- 双方に同じBAN設定を適用し、両パーティがサーバー検証に通ってから対戦を開始します。セルフプレイでは両者の経験を学習に使います。
- 学習時は `team1.txt` を読み込みません。評価時のPPO側は引き続き固定構築です。
- 対戦相手のseedは `cfg.seed + 段階番号（0～2）`、学習側は `cfg.seed + 1000 + 段階番号` として、別々の乱数系列を使います。
- 学習用ユーザー名は生成のたびに一意にします。再起動時に以前の未終了バトルへ再接続して古い指示を送ることを防ぎます。
- ランダム相手とダメージ重視相手はランダム選出、PPOは選出も学習します。
- 報酬は勝利 `+1`、敗北 `-1`、引き分け等 `0`。途中の報酬は `0` です。
- 50戦ごとにPPO更新・保存。対戦数等は `train.py` の `main()` で指定します。
- `ppo_doubles_full_actions.pt` があれば重みを引き継ぎます。段階・累積対戦数・最適化器の状態は復元せず、第1段階から始めます。
- 観測768次元、行動729候補に合法行動マスクを適用。テラスタルを選ぶ行動は未実装です。

2026-10-03の双方ランダム化前のモデルは `checkpoints/before_both_random_20261003_41f48739.pt` にバックアップしました。既存ログとモデル形式は保持しており、通常の `python train.py` は現在の保存重みから継続します。学習を実行すると通常どおり元のモデルパスへ更新結果を保存しますが、このバックアップは更新しません。

### ランダムパーティの範囲

`random_team.py` がインストール済みpoke-envの第9世代データを使用します。

- BANされていないポケモン・特性・技を候補にします。進化前も候補に含まれます。
- 技はその種のデータにある第9世代のレベル技・マシン技から4個選び、少なくとも1個は威力のある攻撃技にします。タマゴ技・配布限定技・過去作限定技は使いません。
- 同種・別フォルムの重複なし、持ち物重複なし、禁止伝説は最大1体、幻は除外します。
- 戦闘中専用フォルムや必須持ち物・必須技のあるフォルムなどは抽選対象外です。全ポケモン・全合法型を網羅する生成器ではありません。
- レベル50、物理寄りならいじっぱりAS、特殊寄りならひかえめCS。持ち物はオボンのみ・たべのこし・きあいのタスキ・いのちのたま・ラムのみ・ぼうじんゴーグルを1個ずつ割り当てます。
- 対戦前に起動中のサーバーへ `/utm` と `/vtm` を送って検証し、受理されたパーティだけを投入します。拒否された場合は記録して再抽選し、最大20回で停止します。
- 検証用接続では初期化完了（`challstr`）を待ってから送信します。初期化・検証応答の待機は各15秒、一時的なタイムアウトは同じパーティで最大3回接続を試みます。失敗時は待機段階・直近の応答・候補パーティをログへ記録します。
- seedは `PPOConfig.seed` を基準に段階ごとに変更します。同じデータ・BAN・検証結果なら同じ抽選系列になります。対戦結果全体の再現性を保証する設定ではありません。

サーバー側検証コマンドの仕様: [Pokemon Showdown公式実装](https://github.com/smogon/pokemon-showdown/blob/master/server/chat-commands/core.ts)。

## BAN設定

`training_bans.json` の `species` / `abilities` / `moves` に、Showdown IDをキー、理由を値として追加します。
設定は各学習段階の開始時に読み込みます。変更を確実に適用するには学習を再起動してください。

```json
"moves": {
  "transform": "種族・技の置換を避ける",
  "allyswitch": "場のスロットの入れ替わりを避ける"
}
```

初期設定では次を予防的に除外します。

- ゾロア・ゾロアークの全フォルム（ヒスイ含む）、メタモン、テラパゴス、イルカマン、シャリタツ。
- イリュージョン・かわりもの・しれいとうなど、個体情報や場の占有状態を大きく変える特性、および一部の自動フォルム変更特性。
- へんしん・サイドチェンジ、ゆびをふる・ねごと・まねっこ等の技呼び出し／技置換、スキルスワップ等の特性置換。

2026-09-29の実行ログで連続使用中の対象指定エラーが確認された `outrage`（げきりん）、`uproar`（さわぐ）、`petaldance`（はなびらのまい）、`thrash`（あばれる）、`ragingfury`（だいふんげき）もBANしています。poke-env 0.9.0の指示とサーバー側の要求が合わず、同じエラーを繰り返すため除外しました。除外漏れを防ぐため `move_targets.randomNormal` により同じ対象分類の技もデータから一括除外します。これは生成・固定パーティの技構成に適用し、PP切れ時にサーバーから指定される「わるあがき」の実行は妨げません。

サーバーで使用不可と確認された相棒ピカチュウ・相棒イーブイ・フラエッテ（えいえんのはな）も抽選から除外しています。通常のピカチュウ・イーブイ・フラエッテは対象に残ります。

`Unexpected effect 'LINGERING_AROMA'` の警告を実対戦で確認したため、「とれないにおい」も特性BANに含めています。poke-env 0.9.0がこの特性による状態変化をUNKNOWNとして処理するためです。他の許可特性を持つパフュートンは出現します。

種族のBANはその別フォルムにも適用します。BAN特性以外の特性が選べる種族は、許可された特性で出現する場合があります。
評価用の固定 `team1.txt` もチェックし、禁止対象が含まれていたら評価開始前にエラーにします。

これらは既知の懸念と複雑な処理を避けるための予防的設定であり、全項目でクラッシュを再現したリストではありません。未知の不具合はエラー記録を見て除外を追加してください。

## エラー記録

2026-10-03の対戦 `battle-gen9vgc2024regg-70539` で、さいきのいのり（`revivalblessing`）の蘇生対象選択を通常交代として扱い、`pass, pass` が拒否されることを確認しました。現行の行動変換は蘇生選択に未対応のため、この技を共通BANに追加しています。ベラカス・パーモット自体は、禁止技を持たない構成で出現します。

通常の学習では実行ごとに新しい `logs/training_errors_<UTC日時>_<識別子>.jsonl` を使い、1件1行のJSONを追記します。開始時に予定の保存先を表示し、記録が発生するまでファイルは作りません。過去の巨大な `training_errors.jsonl` への追記を避け、既存ログは保持します。明示的に `PPOConfig.error_log_path` を指定した場合はその指定を優先します。

ログの作成・追記・書き込み完了時に `OSError` 等が発生した場合は、既存ファイルを変更せず、OSの一時フォルダーにある `pokemonshowdown-training-errors/<run_id>.jsonl` へ自動で切り替えます。Windowsでは通常 `%TEMP%` 配下です。切替先はコンソールの `[WARN] Training error log switched to:` で確認できます。ログのI/O障害だけでパーティ検証や学習を停止することはありません。

学習停止時の `Training battle failed; inspect ...` も、切替後の実際の保存先を表示します。ログ書き込みの `[WARN]` は保存先切替の通知であり、それ自体が対戦失敗の原因ではありません。

両方の保存先が使えない場合は最大100件をメモリーに保持し、次の記録時に再試行します。100件を超えた分は古いものから破棄し、保持中の記録はプロセス終了時には失われます。ログ障害の警告は重複表示しません。本来の対戦エラーは従来どおり処理します。各記録の `event_id` は、書き込み完了時の失敗などで同じ記録が複数ファイルに残った際の照合に使えます。

記録対象は、パーティの拒否、対戦中のサーバーエラー、対戦メッセージ解析・行動選択の例外、行動変換・ダメージ重視プレイヤーで例外からランダム行動へ切り替えた場合、クライアントエラー、タイムアウトです。

| フィールド | 内容 |
|---|---|
| `timestamp`, `run_id`, `player` | 発生時刻、学習段階の実行ID、プレイヤー |
| `battle_tag`, `turn`, `kind` | 対戦・ターン・エラー分類 |
| `error`, `error_type`, `traceback` | エラー内容とPython例外の詳細 |
| `candidate_moves` | 選択した技と受信ログに含まれる技の候補ID |
| `related_moves` | 技の対象取得・スコア計算など、例外発生時に処理中だった技ID（特定できた場合） |
| `selected_moves`, `selected_order` | 直近の選択技と指示。パーティ拒否時は候補パーティの全技とpacked team |
| `recent_move_events`, `protocol_tail` | 使用者付きの技履歴と直近80行の受信情報 |
| `team`, `opponent_team` | 解析済みの種族・技情報 |
| `cause_confirmed` | `false`。候補の技が原因と確定した記録ではない |

受信バッチには、例外発生時にまだ解析されていない行が含まれることがあります。エラーと無関係な技を誤って除外しないよう、記録からの自動BANは行いません。ログを確認し、原因が分かったものを `training_bans.json` に追加します。

poke-envが回復できる選択エラーは記録して処理を継続します。同じ対戦要求（ターン・rqid）で同一エラーの詳細は1回だけ記録し、選択エラーが合計3回に達したら `server_error_retry_limit` を記録して学習を停止します。再送ループとログの大量生成を防ぐための上限です。解析例外などの致命的エラーでも学習を停止し、その対戦をPPO更新に使いません。対戦待ちの上限は `PPOConfig.battle_timeout_seconds`（既定180秒）です。停止後は最後に保存済みの重みから再開できます。

## 動作確認

チーム情報公開の要求には対戦開始後に返答しません。送信中の競合で「Team Preview終了後は公開の受諾・拒否ができない」という通知が届いた場合は `late_team_sheet_reply` として記録し、致命的エラーとして扱いません。

サーバー不要のテスト:

```bash
python -m unittest discover -v
```

サーバーに接続し、3段階を各2戦実行する動作確認:

```bash
python smoke_training.py --battles 2
```

保存済みモデルからの継続も確認する場合は `python smoke_training.py --battles 2 --resume-model ppo_doubles_full_actions.pt` を使用します。読み込み元へは保存せず、更新結果は一時ファイルにだけ保存します。

動作確認用モデルは一時ディレクトリへ保存し、研究用モデルは上書きしません。エラーログは `logs/smoke_errors.jsonl` です。

## 固定チームの総当たり評価

Showdownサーバーを起動した状態で、`doublebattle` ディレクトリから実行します。

```bash
python test_battle_team.py --battles 100
```

`team1.txt`〜`team5.txt` の全10組について各100戦、計1000戦を実施します。
各チームは4組×100戦＝400戦に参加します。`--battles 1` なら全10戦の動作確認です。
双方が保存済みの `ppo_doubles_full_actions.pt` を使用し、合法行動のスコア最大値を選びます。
学習更新・モデル保存は行いません。各組の挑戦側を交互に入れ替えるため、偶数の対戦数を推奨します。
各固定チームに共通BAN検査と第9世代 `gen9vgc2024regg` のサーバー検証を適用します。

チーム別の勝ち・負け・引き分け・勝率、および組み合わせ別の結果を表示します。
勝率は勝数÷終了対戦数で、引き分けも分母に含めます。
結果は毎対戦後に `logs/team_battle_results_<日時>_<識別子>.json` へ保存します。
保存時にアクセス拒否などが発生した場合は3回まで試行し、失敗が続けばOSの一時ディレクトリ内の `pokemonshowdown-team-results` に切り替えて続行します。切り替え先は警告と終了時の `Results:` に表示され、その後の結果も同じファイルに保存します。
途中でエラーが起きた場合も終了済み対戦を保持し、失敗した対戦を敗戦として数えません。
JSONの `complete` が `false` の場合は未完了の集計です。再実行は新しい総当たりを開始します。
エラーログは `logs/team_battle_errors_<日時>_<識別子>.jsonl` です。
`--model PATH` で別の保存モデル、`--output PATH` で結果JSONの保存先を指定できます。
この勝率は現在のモデルによる運用結果であり、チーム自体の一般的な強さを直接示すものではありません。

## 選出時の種族情報

PPOの共通入力は1201次元です。従来の768次元を保持し、選出フェーズのフラグと、自分・相手各6体の公開種族情報を追加しています。各個体には存在フラグ、図鑑番号の11ビット表現、18タイプ、HP・攻撃・防御・特攻・特防・素早さの種族値（255で正規化）を使用します。タイプと種族値は第9世代の種族・フォルムのデータから取得し、相手の実際の技・持ち物・特性・努力値は推測しません。

自分の6体は選出行動の番号と同じ並び、相手の6体は種族名順に入力します。学習・評価・固定チーム総当たりのすべてで同じ入力処理を使用します。
旧768次元モデルを読み込むと既存の重みを保持し、追加部分だけゼロ初期化します。読み込み時にモデルファイルは書き換えません。新情報を判断に反映するには `python train.py` による継続学習が必要です。学習後に保存されるモデルは新入力形式になり、変更前のコードでは読み込めません。

## 評価

```bash
python evaluate.py
```

評価形式:
- PPOエージェント vs ランダム／ダメージ重視。セルフプレイは既定で無効です。
- `gen9vgc2024regg`
- PPO側は `team1.txt`〜`team5.txt` の各固定チームを順に使用。チーム名・相手の種類ごとに勝率を表示します。
- チームプレビューで4体選出
- 各チームでランダム・ダメージ重視を相手に100戦ずつ、5チーム合計1000戦評価します。
- `python evaluate.py --self-play` でセルフプレイを再度有効にできます。その場合は5チーム×3種類×100戦＝1500戦です。
- 相手のパーティは毎戦ランダム生成。学習と同じ `training_bans.json`、技・特性の除外、サーバー検証を適用します。
- 各チーム・各対戦相手に同じseed（`PPOConfig.seed + 10000`）の生成器を使います。同じ検証結果なら同じパーティ系列になります。
- セルフプレイでは同じ保存済みPPOモデルを双方で共有し、両者とも最大スコアの合法行動を選びます。自軍は固定構築、相手はランダム構築のため、勝率が50%になるとは限りません。表示する勝数・勝率は固定構築側から見た値です。
- PPOは合法行動の最大スコアを選び、学習更新・モデル保存は行いません。
- エラー記録先は実行別の `logs/evaluation_errors_<UTC日時>_<識別子>.jsonl`。学習と同じタイムアウト・再送上限・ログ保存先の切替を使用します。
- 短い動作確認は `python evaluate.py --battles 1`（各チーム・各相手1戦、合計10戦）で実行できます。`--battles` はチームと相手の組み合わせごとの対戦数です。

## 注意
poke-envのバージョンによって、DoubleBattleOrderの生成APIに差分がある場合があります。
その場合は `action_mapper.py` の `action_to_order()` を調整してください。
現在は無効行動時に `choose_random_doubles_move()` へフォールバックします。
